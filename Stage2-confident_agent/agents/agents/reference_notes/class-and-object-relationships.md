# Class and Object Relationships
keywords: aggregation, acquaintance, association, object relationships, design pattern categories, creational, structural, behavioral, class scope, object scope
- Aggregation: one object owns or is responsible for another ("having" or "being part of"); the aggregate and its owner have identical lifetimes. Shown with a diamond-based arrowhead line.
- Acquaintance (also called "association" or the "using" relationship): an object merely knows of another; acquainted objects may request operations of each other but are not responsible for each other. A weaker relationship than aggregation with much looser coupling. Shown with a plain arrowhead line.
- They are easy to confuse because both are usually implemented with pointers/references (in Smalltalk there is no language distinction; in C++ aggregation may use real member instances but more commonly pointers). The distinction is one of intent.
- Aggregation relationships tend to be fewer and more permanent; acquaintances are made and remade more often, sometimes lasting only one operation, and are harder to discern in source code.
- Compile-time vs run-time structure: code structure (classes, fixed inheritance) is frozen at compile-time, whereas run-time structure is a changing network of communicating objects; the two are largely independent. Composite and Decorator help build complex run-time structures; Observer and Chain of Responsibility give run-time structures not revealed by inheritance.
- Creating objects: an object is created by instantiating a class (allocates storage for instance variables and associates operations); the notation uses a dashed arrowhead line from the instantiating class to the class of the instantiated objects. Abstract classes cannot be instantiated; concrete classes can.
- Creating objects by naming a class explicitly commits you to an implementation; the book says to create objects indirectly (Abstract Factory, Factory Method, Prototype).
- Classification by purpose: Creational (the process of object creation), Structural (composition of classes or objects), Behavioral (how classes or objects interact and distribute responsibility).
- Classification by scope: Class patterns deal with class/subclass relationships fixed at compile-time through inheritance; Object patterns deal with object relationships that can change at run-time. Most patterns are object-scoped. Only Factory Method, Adapter (class version), Interpreter and Template Method are class-scoped in Table 1.1.
- Creational class patterns defer object creation to subclasses, object ones to another object; Structural class patterns use inheritance to compose classes, object ones assemble objects; Behavioral class patterns use inheritance for algorithms and control flow, object ones have groups of objects cooperate on tasks no single object can do. The book also notes patterns can be organized by use together (Composite with Iterator/Visitor), alternatives (Prototype vs Abstract Factory) or similar structure (Composite vs Decorator).
