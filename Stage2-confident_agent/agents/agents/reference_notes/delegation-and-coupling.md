# Delegation and Coupling
keywords: delegation, coupling, tight coupling, loose coupling, delegate, abstract coupling, dependencies, reuse, composition, redesign
- Delegation: two objects handle a request; a receiving object delegates operations to its delegate, analogous to a subclass deferring requests to its parent class. It is a way of making composition as powerful for reuse as inheritance.
- With inheritance an inherited operation can refer to the receiving object via this/self; with delegation the receiver must pass itself to the delegate to get the same effect.
- Book example: instead of Window being a subclass of Rectangle, Window keeps a Rectangle instance and forwards Rectangle-specific operations (e.g. Area) to it ("has a" instead of "is a"). Replacing the Rectangle with a Circle of the same type changes the window's shape at run-time.
- Advantage: easy to compose behaviors at run-time and change how they are composed. Disadvantage: dynamic, highly parameterized software is harder to understand than static software, plus some run-time inefficiency; good only when it simplifies more than it complicates, and works best in standard, stylized patterns.
- Patterns depending on delegation: State (delegates to a State object), Strategy (delegates a request to a strategy object), Visitor (the operation is always delegated to the Visitor). Used less heavily by Mediator, Chain of Responsibility (when the request carries a reference to the original receiver) and Bridge (abstraction delegates to implementation).
- Delegation is described as an extreme example of object composition; it shows inheritance can always be replaced by composition for reuse.
- Tight coupling (cause of redesign #6): tightly coupled classes are hard to reuse in isolation and lead to monolithic systems where a class cannot be changed or removed without understanding and changing many others, a dense mass hard to learn, port and maintain.
- Loose coupling: raises the chance a class can be reused alone and that the system is easier to learn, port, modify and extend. Patterns achieve it through abstract coupling and layering; the book lists Abstract Factory, Bridge, Chain of Responsibility, Command, Facade, Mediator and Observer as addressing tight coupling.
- Dependencies between classes: the book lists causes of redesign tied to dependencies (specifying a class when creating objects; specific operations; hardware/software platform; object representation or implementation; algorithms), each with patterns that address them. Acquaintance is a weaker relationship than aggregation and implies much looser coupling.
- Note: the text has no formal definition of coupling metrics beyond these passages (coverage is brief).
