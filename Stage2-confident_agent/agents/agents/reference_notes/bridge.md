# Bridge
keywords: bridge, bridge pattern, handle/body, decouple abstraction from implementation, implementor
- Intent: decouple an abstraction from its implementation so the two can vary independently. Also known as Handle/Body. Object structural.
- Problem addressed: with plain inheritance (abstract Window with XWindow and PMWindow subclasses), implementation is permanently bound to the abstraction, every new window kind needs a class per platform, and client code becomes platform-dependent.
- Use to avoid a permanent binding between abstraction and implementation (e.g. implementation selected or switched at run-time); when both abstractions and implementations should be extensible by subclassing; when implementation changes should not affect clients (no recompilation).
- Also use to resolve a proliferation of classes (a sign the object should be split into two parts), or to share an implementation among objects (e.g. reference-counted string representation) hidden from the client, or (C++) to hide the implementation fully.
- Participants: Abstraction (interface; holds a reference to an Implementor), RefinedAbstraction (extends the abstraction), Implementor (interface for implementation classes; typically only primitive operations, and need not match the Abstraction's interface), ConcreteImplementor. The Abstraction forwards client requests to its Implementor.
- Benefits: decouples interface and implementation (implementation can be configured or changed at run-time; no compile-time dependency); improved extensibility (hierarchies extend independently); hides implementation details from clients.
- Known uses: ET++ Window/WindowPort (the implementor is obtained from an abstract factory, WindowSystem); NeXT AppKit NXImage/NXImageRep; libg++ Set (degenerate bridge with no abstract Implementor).
- Related: an Abstract Factory can create and configure a particular Bridge. Adapter makes unrelated classes work together and is usually applied after systems are designed; Bridge is used up-front so abstractions and implementations vary independently. Adapter's related-patterns note says Bridge's structure is similar to an object adapter but its intent differs.
- Structural discussion: both Adapter and Bridge provide indirection and forward requests; the key difference is intent. Adapter makes independently designed classes work together after the fact; Bridge provides a stable interface while the implementing classes vary.
