# Decorator
keywords: decorator, decorator pattern, wrapper, add responsibilities dynamically, alternative to subclassing
- Intent: attach additional responsibilities to an object dynamically; a flexible alternative to subclassing for extending functionality. Also known as Wrapper. Object structural.
- Use to add responsibilities to individual objects dynamically and transparently, without affecting other objects; for responsibilities that can be withdrawn.
- Use when extension by subclassing is impractical: many independent extensions would cause an explosion of subclasses for every combination, or the class definition is unavailable for subclassing.
- Participants: Component (interface for objects that can have responsibilities added), ConcreteComponent, Decorator (holds a reference to a Component and conforms to its interface), ConcreteDecorator (adds responsibilities). The Decorator forwards requests to its Component, optionally doing extra work before or after.
- Because the decorator conforms to the component's interface, it is transparent to clients and decorators can be nested recursively (e.g. BorderDecorator and ScrollDecorator around a TextView).
- Benefits: more flexible than static inheritance (responsibilities added/removed at run-time; the same one can be added twice); avoids feature-laden classes high in the hierarchy (pay-as-you-go).
- Liabilities: a decorator and its component are not identical, so do not rely on object identity; results in lots of little, similar-looking objects that are hard to learn and debug.
- Known uses: UI toolkits (Interviews, ET++, ObjectWorks\Smalltalk) adding borders/scrolling; ET++ streams (CompressingStream, ASCII7Stream wrapping a FileStream).
- Distinguishing (book): Adapter gives an object a completely new interface, whereas a decorator only changes responsibilities, not the interface. Composite: a decorator is like a degenerate composite with one component, but adds responsibilities and is not for aggregation. Strategy: a decorator changes the "skin" of an object; a strategy changes the "guts".
- Structural discussion: Composite and Decorator share recursive composition but differ in intent (Decorator adds responsibilities; Composite structures objects for uniform treatment and representation). They are complementary and often used together; a composite is a ConcreteComponent from the Decorator viewpoint, and a decorator is a Leaf from the Composite viewpoint. Versus Proxy: Decorator is for open-ended functionality that cannot conveniently be determined at compile time, so recursive composition is essential.
