# Design Principles
keywords: design principles, program to an interface, favor composition over inheritance, composition, inheritance, class inheritance, interface inheritance, reuse, white-box reuse, black-box reuse
- Principle 1: "Program to an interface, not an implementation." Do not declare variables as instances of concrete classes; commit only to an interface defined by an abstract class.
- Benefits: clients stay unaware of the specific types of objects they use, and unaware of the classes implementing them, so implementation dependencies between subsystems are greatly reduced. Relies on polymorphism and dynamic binding (substituting objects with identical interfaces at run-time).
- Concrete classes must still be instantiated somewhere; the creational patterns (Abstract Factory, Builder, Factory Method, Prototype, Singleton) do this by abstracting object creation so the system is written in terms of interfaces.
- Principle 2: "Favor object composition over class inheritance." Designers overuse inheritance; designs are often more reusable and simpler with object composition. Inheritance and composition work together, since inheritance makes it easier to make new components to compose.
- Inheritance is white-box reuse: defined statically at compile-time, straightforward to use, easier to modify what is reused. Drawbacks: cannot change inherited implementation at run-time; exposes subclass to parent implementation ("inheritance breaks encapsulation"), so parent changes force subclass changes. One cure is to inherit only from abstract classes.
- Composition is black-box reuse: defined dynamically at run-time via references; objects are accessed only via interfaces so encapsulation is kept, any object can be replaced by another of the same type, and implementation dependencies fall. Trade-off: more objects (fewer classes), and behavior depends on their interrelationships rather than being defined in one class.
- Class vs type: an object's class defines its implementation (state and operations); its type refers only to its interface (the requests it answers). An object can have many types, and objects of different classes can share a type.
- Class inheritance defines an object's implementation in terms of another's (code and representation sharing); interface inheritance (subtyping) describes when one object can be used in place of another. Many languages (C++, Eiffel) conflate them; in Smalltalk inheritance is implementation inheritance only.
- Patterns relying on the distinction: Chain of Responsibility objects need a common type but usually not a common implementation; in Composite, Component gives a common interface while Composite often gives a common implementation; Command, Observer, State and Strategy are often implemented with abstract classes that are pure interfaces.
- Related reuse option (inheritance vs parameterized types): sorting by a comparison can be done by Template Method (subclass), Strategy (passed object) or a C++ template/Ada generic; only composition can change behavior at run-time.
